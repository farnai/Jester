## 2. Token / Context Observability Architecture (Phase 2D)

Phase 2D introduces lightweight, vendor-neutral token observability across all bridge providers and workflow lifecycle stages:

1. **Normalized Contract (`UsageMetrics` in `jester_bridge/contracts.py`):**
   - Encapsulates `input_tokens: Optional[int]`, `output_tokens: Optional[int]`, and `total_tokens: Optional[int]`.
   - Includes cumulative helper method `UsageMetrics.add(other)` handling partial or `None` fields.
   - Added `usage: Optional[UsageMetrics] = None` to `InvocationResult`.
2. **Provider Mapping:**
   - **OpenAIProvider (`jester_bridge/openai_provider.py`):** Maps `response.usage.prompt_tokens`, `completion_tokens`, and `total_tokens` directly to `UsageMetrics`.
   - **GoogleProvider (`jester_bridge/google_provider.py`):** Maps `response.usageMetadata.promptTokenCount`, `candidatesTokenCount`, and `totalTokenCount` directly to `UsageMetrics`.
   - **BaseMockProvider (`jester_bridge/testing.py`):** Provides predictable default usage metrics (100 in / 50 out / 150 total) for deterministic testing.
3. **Zero Provider Branching in Orchestration:**
   - Zero vendor-specific branching (`if provider == "openai": ...`) exists in `BridgeCore`, `BridgeOrchestrator`, or `ControlledWorkflowRunner`.
   - Token metrics are extracted and manipulated strictly through the normalized `InvocationResult.usage` interface.
4. **Session Aggregation:**
   - `OrchestrationSession.get_total_usage()` computes the cumulative tokens across completed stages (`architect`, `executor`, `reviewer`).
   - `OrchestrationSession.get_stage_usage()` returns a per-stage dictionary breakdown containing role, provider, model, and token metrics.
5. **Report & CLI Integration:**
   - Implementation reports embed executor token usage under `## Token Observability`.
   - Review reports embed both reviewer tokens and the cumulative workflow aggregate tokens under `## Token Observability`.
   - CLI runner prints formatted token breakdown by stage and total token count in the execution summary.

## 3. Portability Hardening & Sanitization (Phase 2D)

Phase 2D eliminates all machine-specific absolute paths and URLs from generated task files, reports, and workflow outcomes:

1. **Root Cause Analysis:**
   - Previous reports retained machine-specific paths because Windows drive letters in lowercase `file:///c:/...` and complex non-greedy regex patterns failed to strip preceding user path components.
2. **Comprehensive Sanitizer (`sanitize_portable_paths` in `jester_bridge/workflow.py`):**
   - Strips all `file:///` URLs referencing the repository root or internal folders.
   - Strips absolute filesystem paths (`C:\Users\...`, `C:/Users/...`, `/Users/...`, `/home/...`) leading into the repository.
   - Normalizes Windows backslashes in repository paths to standard forward slashes (`/`).
   - Converts external user directory paths to generic portable `~/`.
3. **Outcome Path Normalization (`ControlledWorkflowRunner._rel_path`):**
   - Guarantees all paths in `WorkflowOutcome` (`task_file_path`, `implementation_report_path`, `review_report_path`) are repository-relative POSIX strings.
   - CLI execution output exclusively displays repository-relative paths.
