## 🃏 1. Executive Summary & Architectural Paradigm

**JESTER** is a **People Discovery and Relationship Intelligence** engine.
Astrology provides the deterministic, mathematical intelligence layer, but **JESTER is not positioned as an astrology app**.
The product is about human connection, personality dynamics, and relationship intelligence:
> *"They show the match. JESTER explains the connection."*

### The Core Architectural Axiom: Rejection of $1\text{ Signal} = 1\text{ Text}$

Content Architecture V2 explicitly rejects the naive model where one astrological aspect maps to a single hardcoded sentence.
Instead, JESTER implements a decoupled 5-layer pipeline:

```text
Layer A: ASTROLOGICAL CALCULATION (PySwissEph, Synastry V1)
      ↓ (Deterministic planetary positions, orbs, aspects, scores)
Layer B: ASTROLOGICAL SIGNAL (e.g., venus_mars_aspect, strength 0.91)
      ↓ (Deterministic mapping to human relationship meaning)
Layer C: SEMANTIC INTERPRETATION (e.g., relationship.attraction.strong_chemistry.v1)
      ↓ (Voice persona, constraints, brevity, tone directives)
Layer D: VOICE & EDITORIAL CONSTRAINTS (Tone: witty/playful/soft/bold/savage/romantic)
      ↓ (Multi-asset catalog: hundreds/thousands of copy assets)
Layer E: CONTENT ASSET LIBRARY (ka, en, approved, ai_draft, variants)
      ↓ (Context, locale, tone, status hierarchy, seed-based rotation)
DETERMINISTIC CONTENT RESOLVER
      ↓
RESOLVED USER COPY (Safe, jargon-free, rendering-ready JSON)
```

### Architectural Invariants
1. **Mathematical Independence**: The astrology engine (`calculator.py`, `aspects.py`, `synastry.py`) knows **nothing** about copy, Georgian strings, tones, variants, or editorial metadata.
2. **Semantic Meaning Independence**: Semantic interpretations describe **WHAT** is happening in psychological/relational terms. They contain **zero user-facing copy strings**.
3. **Copy Multiplicity**: A single semantic meaning has **many** copy assets across tones, personas, variants, contexts, and locales.
4. **Copywriter Dominance**: Approved copywriter assets **always beat** temporary AI launch drafts.
5. **Archived Isolation**: Archived assets are strictly and permanently excluded from resolution.
6. **Zero Jargon Invariant**: Consumer copy contains 0% technical astrology jargon (*conjunction, trine, orb, synastry, etc.*).
7. **Stateless Frontend Contract**: The client application receives rendered user copy. It contains zero astrology rules or interpretation logic.

## 🏛️ 2. Domain Models & Architecture

All domain models are formally defined in [backend/app/interpretation/models.py](file:///c:/Users/fiord/OneDrive/Desktop/Jester/backend/app/interpretation/models.py).

### 2.1 The `ContentAsset` Domain Model

```python
class ContentAsset(BaseModel):
    asset_id: str                          # Stable unique identifier, e.g. ca_rel_chem_001_ka_witty_a
    interpretation_id: str                 # Link to semantic contract, e.g. relationship.attraction.strong_chemistry.v1
    locale: str = "ka"                     # IANA language code (ka, en)
    context: str = "relationship"          # Product context (relationship, daily_energy, friendship, etc.)
    tone: str = "witty"                    # Voice persona (witty, playful, soft, bold, savage, romantic)
    persona: str = "jester"                # Brand persona
    text: str                              # Consumer-facing prose (zero jargon)
    status: ContentStatus = "ai_draft"     # draft, ai_draft, review, approved, experimental, winner, archived
    version: int = 1                       # Monotonic copy version
    priority: int = 100                    # Editorial weight / priority override
    variant_key: str | None = None         # A/B variant key (variant_a, variant_b, etc.)
    source: str = "copywriter"             # ai | copywriter | agency | system
    author: str | None = None              # Internal author attribution
    tags: list[str] = Field(default_factory=list)
    internal_notes: str | None = None      # Internal copywriter notes (hidden from non-editors)
    experiment_id: str | None = None       # Associated A/B experiment flag
    weight: float = 1.0                    # Relative probability weight
    archived: bool = False                 # Soft deletion flag
    created_at: datetime
    updated_at: datetime
```

### 2.2 Content Status Lifecycle

```text
[DRAFT]
   ↓
[AI_DRAFT] ──────→ [REVIEW] ──────→ [APPROVED] ──────→ [WINNER]
   ↓                                    ↓
[EXPERIMENTAL] ─────────────────────────┘
   ↓
[ARCHIVED] (Excluded from all resolution)
```

- **`draft`**: Incomplete or scratch copy.
- **`ai_draft`**: Automated launch copy generated by batch LLM workflows. Fully validated for jargon and safety, serving as production-ready fallback until reviewed.
- **`review`**: Copy queued for copywriter review.
- **`approved`**: Verified, high-impact copywriter prose. Immediately takes priority over AI drafts.
- **`experimental`**: Variant undergoing A/B testing (resolved only when `include_experimental=True`).
- **`winner`**: Outperforming experiment variant promoted to permanent tier 1 status.
- **`archived`**: Deprecated or retired copy. Guaranteed never to resolve.

## ⚙️ 3. Deterministic Content Resolution Algorithm

The resolution algorithm ([ContentResolver](file:///c:/Users/fiord/OneDrive/Desktop/Jester/backend/app/interpretation/library.py)) deterministically maps runtime requests to the optimal content asset:

```text
Resolver Inputs:
(interpretation_id, context, locale, tone, variant_key, seed, include_experimental)
```

### Step-by-Step Resolution Execution:
1. **Contract Validation**: Verify that `interpretation_id` exists in `INTERPRETATION_CONTRACTS`. Reject unknown/invented IDs (returns `None`).
2. **Context Matching & Fallback**:
   - Query non-archived assets matching `(interpretation_id, context, locale)`.
   - If no assets match the requested context, fall back to assets matching `(interpretation_id, fallback_context)`.
3. **Locale Matching & Fallback**:
   - If no candidates match the requested locale (e.g. `de`), fall back to Georgian (`ka`) or English (`en`).
4. **Tone Preference Filtering**:
   - If `tone` is specified (e.g. `playful`), filter candidates matching that tone.
   - If no candidates match that specific tone, gracefully keep the candidate pool as a fallback.
5. **Status Hierarchy Evaluation**:
   - **Tier 1 (Approved / Winner)**: Filter candidates where `status in ("approved", "winner")`. If found, this pool wins unconditionally.
   - **Tier 2 (Experimental)**: If `include_experimental=True`, filter `status == "experimental"`.
   - **Tier 3 (AI Draft)**: Filter `status == "ai_draft"`.
   - **Tier 4 (Draft)**: Non-empty draft text.
6. **Variant Key Matching**: If a specific `variant_key` is requested, filter matching assets.
7. **Deterministic Sorting**: Sort eligible pool by `(-priority, -version, asset_id)`.
8. **Repetition Management & Seed Rotation**:
   - If `seed` is provided (e.g. user ID or connection ID):
     $$\text{hash} = \text{SHA256}(\text{seed} : \text{interpretation\_id} : \text{context}) \pmod N$$
   - The selected index guarantees stable, repeatable variant delivery for the same user while rotating across distinct users.

## 🎭 4. Voice Personas & Product Context Taxonomy

### 4.1 Voice Personas
- **`witty`**: Observant, clever, socially intelligent, signature JESTER brand voice.
- **`playful`**: Lighthearted, mischievous, energetic banter.
- **`soft`**: Warm, gentle, emotionally supportive, subtle.
- **`bold`**: Direct, punchy, slightly provocative without being vulgar.
- **`savage`**: Sharp observational humor without ever being cruel or humiliating.
- **`romantic`**: Warm, chemistry-focused language free from generic horoscope clichés.

### 4.2 Product Context Taxonomy
- **`relationship`**: Synastry connection analysis, compatibility overview, dynamic insights.
- **`friendship`**: Platonic social connections and shared cadence.
- **`business`**: Professional synergy, communication flow, collaborative friction.
- **`daily_energy`**: Personal transit insights, daily focus, reflective prompts.
- **`deep_analysis`**: Traceable breakdown with astrological evidence tags and dimension deep-dives.
- **`discovery`**: Browse cards and initial impression previews.
- **`onboarding`**: Initial natal personality reveal.
- **`notification`**: Push notifications and in-app event teasers.
- **`share`**: Viral social sharing cards and connection links.

## 💾 5. Storage Abstraction & CMS Migration Boundary

The architecture enforces a strict storage abstraction boundary via the `ContentStore` abstract base class:

```python
class ContentStore(ABC):
    @abstractmethod
    def get_asset(self, asset_id: str) -> ContentAsset | None: ...
    @abstractmethod
    def list_assets(self, ...) -> list[ContentAsset]: ...
    @abstractmethod
    def save_asset(self, asset: ContentAsset) -> ContentAsset: ...
    @abstractmethod
    def delete_asset(self, asset_id: str) -> bool: ...
    @abstractmethod
    def archive_asset(self, asset_id: str) -> ContentAsset | None: ...
```

### 5.1 Current Implementation: `InMemoryContentStore`
- Thread-safe (`threading.RLock`) indexed in-memory dictionary.
- Sub-millisecond lookup and filtering over thousands of assets.
- Pre-seeded with production-quality Georgian (`ka`) and English (`en`) copy across all 30 interpretation contracts.

### 5.2 Future PostgreSQL / Headless CMS Integration Boundary
When scaling to tens of thousands of assets with headless CMS tooling (e.g., Strapi, Sanity, or Supabase PostgreSQL tables):
1. Implement `PostgresContentStore(ContentStore)`.
2. Connect `ContentLibrary(store=PostgresContentStore(pool))`.
3. **Zero code changes** required in the astrology engine, synastry engine, resolver algorithms, API schemas, or frontend clients.
